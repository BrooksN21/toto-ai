## 1. Владелец и границы

Единственный координатор и владелец production — родительская задача
`019f7afa-72e2-7403-85cd-d05f408a4ef3`, checkout `/Users/turshevr/toto-ai`.
Только она принимает результаты, разрешает интеграцию и ведёт операционный контур.
Дочерние задачи работают в собственных подтверждённых worktree; им запрещены
запись в родительский checkout, рабочую БД, scheduler, operator-артефакты,
активация, push и публикации. Неизвестный checkout — запрет на запись.
Пользователь решает вопросы стратегии, денег и удалённой передачи; не переносит
контекст вручную между задачами. Разделение задач не расширяет полномочия.
Production cwd закреплён только за operations-владельцем. Дети явно задают свой
подтверждённый cwd; production читают только read-only. Перед Git проверяют,
что локальный `scripts/project-git` действительно закреплён за их checkout,
а не за production; неизвестная/родительская привязка блокирует child Git.

**Worktree изолирует файлы, но не CPU, RAM, процессы и квоты публичных API хоста.**
Production-задания имеют приоритет: тяжёлые replay, обучение и большие тесты
не должны конкурировать с ними в запланированное операционное окно и перед
дедлайном. До запуска сверять окно по родительскому checkpoint; при неизвестном
окне тяжёлую работу не начинать. При пересечении сохранять checkpoint и
приостанавливать только собственные исследовательские задания с подтверждённой
принадлежностью; неизвестные процессы не завершать и production не трогать.
Экспериментальный CLI обязан явно использовать БД и output-пути своего worktree;
вход из production — только замороженные read-only экспорты. Не полагаться на
неявные абсолютные production-defaults: при неподтверждённых путях запуск запрещён.

## 3. Минимальный durable recovery contract

Единственный центральный реестр — `memory-bank/THREAD_COORDINATION.json`;
короткий operational checkpoint родителя остаётся `memory-bank/ACTIVE_PLAN.md`.
Отдельный `ORCHESTRATOR_CHECKPOINT.md` не нужен. Шаблон детского checkpoint
встроен в реестр (`child_checkpoint_template`), без дублирующих систем памяти.
Каждый ребёнок после подтверждения собственного ID/checkout сохраняет там один
короткий checkpoint ДО значимой работы; неизвестные baseline/hash отмечает null
и блокирует зависимую работу. Затем возвращает родителю реальный ID, cwd, путь
checkpoint и принятые границы. До этого startup ACK остаётся pending.

Каждый checkpoint содержит роль/ID/родителя, абсолютный checkout, разрешённые
пути записи, принятый ref и полный hash, dirty-зависимости и их fingerprint,
ссылки на evidence/согласия, сделано/осталось/блокер, один точный следующий шаг,
время или условие проверки, ожидаемое согласование. Для активной команды:
PID/session, время старта, команда/cwd, журнал, ожидаемый результат; иначе `none`.
Обновлять после существенного результата и перед длительным запуском/передачей,
фиксируя выход и проверенное свидетельство завершения. Не переписывать всю память.

На старте и после compaction:
1. Прочитать собственный checkpoint; сверить свою роль, ID, checkout и границы.
2. Подтвердить baseline и учтённые dirty-зависимости. Несовпадение — остановить
   зависимую работу и сообщить родителю, не переключать/обновлять checkout молча.
3. Проверить только записанный активный PID/session и его принадлежность команде,
   cwd и времени запуска; один номер PID недостаточен. Живой запуск продолжать
   наблюдать, завершённый принять по журналу/артефакту. Неизвестное состояние
   требует уточнения; оно не даёт права повторять команду или создавать job.
4. Читать только ограниченный фрагмент связанного evidence для конкретной
   неопределённости; выполнить собственный следующий шаг без повторного аудита
   истории и перезапуска уже выполненной работы.

**Дочерний checkpoint определяет следующий шаг ребёнка, а не родительский
ACTIVE_PLAN. Никогда не выполнять production `NEXT COMMAND` как команду ребёнка.**
ACTIVE_PLAN для детей — общая read-only справка. Это разграничение next-action,
не отмена защитных правил. Если локальный checkpoint отсутствует или противоречив,
запросить точечный handoff родителя; не наследовать его операционный шаг.
Реестр описывает координацию, локальный checkpoint — исполнение конкретной роли;
расхождение о полномочиях или базе блокирует зависимую работу до согласования.

## 5. Доставка статуса и критерий готовности договора

Родитель даёт здесь один сводный статус: сделано / выполняется / осталось /
блокер / следующий точный checkpoint. Во время активного обращения доступны
чтение и ожидание результатов; Python-watcher не будит idle-чат, heartbeat
запрещён. Нет обещания автономных сообщений или абсолютно несбрасываемой памяти.
Локальные hooks/schema/checks добавлять только при доказанной необходимости
и в отдельной реализации; наличие файла само по себе не гарантирует его чтение.

Договор считается внедрённым лишь после подтверждения настоящих ID и checkout,
заполнения реестра, сохранения собственных checkpoints и проверки, что каждая
роль восстанавливает свой шаг, не production-команду родителя. Сейчас дети не
подтверждены, baseline не принят; готовность к экспериментам не заявляется.
