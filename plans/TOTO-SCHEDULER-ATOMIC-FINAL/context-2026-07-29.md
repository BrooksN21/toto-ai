## Four exact reproductions

The network-free reproduction used the current scheduler test fixtures and a
fake clock. Evidence is under
`reports/rehearsal/context-4959-20260729/reproductions/`.

1. **Stale post-preparation T−45 time.** A preflight starting at `11:15`
   simulated preparation completion at `11:19`; the subsequent target validator
   still received `11:15`. `CommandSchedulerPhaseRunner` calls `_preflight()`
   and then passes `context.started_at` to `target_validator`
   (`scheduler.py:2030-2034`), so post-preparation validation can accept a target
   using a stale clock.
2. **Orphan actionable bytes after late recovery.** After a valid archive was
   created, its `.bet-ready` marker was removed to reproduce a crash, state was
   reset, and the next tick ran one second after T−12. Result: terminal
   `no-bet`, no `.bet-ready`, but both `package.csv` and
   `package-archive.json` remained. Recovery runs before the normal terminal/
   deadline checks (`scheduler.py:1378-1397`); its late branch calls
   `_finalize_tick_no_bet()` without removing actionable bytes
   (`scheduler.py:1618-1687`).
3. **Inaccurate `captured_at`.** A detail request simulated to complete nine
   seconds after attempt start persisted `captured_at=11:40:00`, not the
   response completion time `11:40:09`. Capture is explicitly called with
   `captured_at=context.started_at` (`scheduler.py:2040-2052`).
4. **Publication reserve unenforced.** With the configured 45-second reserve,
   the fake clock completed final work only 30 seconds before T−12; the current
   code still produced `.bet-ready`. The reserve is checked only when admitting
   an attempt/retry (`scheduler.py:1436-1447`, `1488-1498`). Archive and marker
   publication enforce only T−12 itself (`scheduler.py:2638-2649`,
   `2817-2829`), not `T−12 − publication_reserve`.
